# Registry, management and settings application integration

**Status: owner-approved design; isolated fixture and required shared internal adapters implemented / unmerged in PR #81.** The owner approved all design choices and numerical fixture budgets in this guide. Implementation authorization stops at the fixture and its required internal adapters. These budgets are not release defaults. Normal application rollout and publication enablement remain outside this approval. See the [fixture README](../../prototypes/application-integration/README.md) for commands and the [consolidated changelog section](change-log.md#consolidated-application-integration-design) for validation.

## Purpose and current boundary

Application integration connects startup ownership, a plugin-free manager, durable settings saves and per-workspace application. These responsibilities cannot be implemented safely as unrelated UI wrappers. This guide records their approved contracts and the implemented isolated fixture. It also identifies production work that remains planned.

The current [Tauri builder](../../src-tauri/src/lib.rs) registers `greet` and opener, not the registry. [Application configuration](../../src-tauri/tauri.conf.json) creates one window with CSP disabled. Its [capability](../../src-tauri/capabilities/default.json) grants core/opener defaults to `main`. The [main route](../../src/routes/+page.svelte) imports and activates bundled plugins and renders its manager in that same WebView. That dialog is not the approved separate native management boundary.

The implemented [registry lifecycle](registry-implementation-review.md#lifecycle-invalidation-and-observation--current-implementation) and [native settings coordinator](resource-settings-plan.md#internal-rust-coordinator-and-remaining-production-integration) provide real persistence, invalidation and bounded internal observation. The isolated fixture now adds a settings wire format, management authorization and frontend transport around these services. Normal production startup remains unwired. Rust `SettingsEpoch` is allocation-based, not a wire identity. Native snapshot subscriptions do not deliver a closed notification to JavaScript.

The separate [resource-loading prototype](resource-loading-investigation.md) demonstrates isolated packaging, explicit capabilities and native window/resource associations. Its macOS results do not establish settings authorization for this fixture. Registry cleanup requires separately awaited draining.

## Approved scope

| Decision            | Approved choice                                                                                                                 | Main tradeoff                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Startup and storage | One application-owned bootstrap state machine; fixed local application-data layout; no fallback selection or alternate registry | Failures remain visible instead of silently creating usable-looking defaults   |
| Failed opening      | Retain a location owner and expose an opening-attempt cleanup handle, including on failure                                      | Requires separate readiness and cleanup ownership                              |
| Management          | One native-created, plugin-free management/recovery WebView with lifetime-bound Rust authorization                              | Requires a separate build entry and capability inventory, not an editor dialog |
| Transport           | Tauri channels for targeted full snapshots, explicit acknowledgments and bounded liveness renewal                               | Requires bounded health messages without database polling                      |
| UI and rollout      | Settings form in the manager; opt-in command assembly only in the fixture first                                                 | The existing default bundled host stays unchanged                              |
| Validation scope    | Separate packaged fixture over preseeded disposable storage; no publication path                                                | Tests real integration without proving first-run creation or durability        |

All choices in this table and the budgets below are approved for fixture-only implementation. The fixture and shared internal adapters are implemented. Production rollout remains separate.

## Application startup and ownership

### Storage layout

**Planned production placement, not fixture behavior:** resolve the platform's local application-data directory through Tauri using the existing application identifier. The fixture instead requires a runner-owned disposable parent and never falls back to real app data. Under that host-managed parent, use `registry/`, its existing sibling `registry.location-lock`, and `registry-upgrade-backups/`. Prepare only the stable parent before acquiring `LocationLease`. Perform blocking path and lock work off latency-sensitive executor threads. No frontend supplies a root, database path or backup destination.

Acquire the lease before testing the dedicated root. An absent root is eligible for first initialization; an existing empty root is not. Permission errors, unknown metadata and I/O errors are not absence. Read the strict `active` selector and validate the named generation with the existing no-follow helpers before opening SQLite. Never scan directories for a fallback generation. The containment check in `Registry::open_owned` does not replace selector validation.

Production first initialization and replacement remain blocked by the current publication gate. An absent root therefore produces `InitializationBlocked` without creating that root. Production storage that fails selection or readiness must enter recovery UI, not a replacement registry. The fixture reports those startup failures and cleanup status without opening a recovery window. Local application-data placement is not proof of a qualified storage stack.

### Approved application states and fixture coverage

| State                          | Meaning                                                                                                                                          |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Starting(stage)`              | Preparing paths, acquiring ownership, validating selection, opening/upgrading, or loading settings; no settings-integrated command admission     |
| `OwnershipUnavailable(reason)` | Ownership was not acquired; no database inspection or takeover; offer exit and explicit retry                                                    |
| `InitializationBlocked`        | Root is absent but first publication is unavailable; no automatic creation                                                                       |
| `RecoveryRequired(reason)`     | Selection, opening, upgrade, or live service invalidation prevents normal operation                                                              |
| `SettingsUnavailable(reason)`  | Registry is healthy but authoritative settings startup failed, such as reader-cap refusal; retain the registry owner, expose no guessed settings |
| `Ready`                        | Registry and native settings service are ready; each workspace still needs its own initial settings application                                  |
| `ShuttingDown`                 | Sticky admission closure and ordered draining                                                                                                    |
| `Stopped(outcome)`             | Cleanup completed or its failure was reported; not a claim that every earlier uncertain write rolled back                                        |

These are application states, not new values fabricated inside `LifecycleSnapshot`. Pre-open failures have no registry lifecycle revision. Distinguish lock contention from inability to create/open the lock. The current text-only `Unavailable` mapping does not justify saying every lock failure means another live instance. The shared `LocationLease::acquire_detailed` adapter preserves structured contention, open and lock failures.

Registry ownership refusal is not application single-instance forwarding. Existing approved launch-during-finalization behavior still needs a separate process/session handoff design. The fixture includes a second-process refusal check without takeover. It does not implement launch forwarding. The full production state machine and recovery interface remain planned; fixture startup reports bounded failures and cleanup status.

### Opening failure and cleanup

Retain an application-owned lease clone across selection, opening and failure presentation. Do not make a ready operation handle the owner of that location. The shared `Registry::begin_owned` opening-attempt contract exposes startup completion and awaited worker cleanup separately. A successful outcome transfers the ready `RegistrySession`; a failed outcome preserves the original error and a cleanup owner. It exposes no usable operation handle. Selection failures before spawning have no worker to drain.

`RegistryOpening::complete().await` transfers ownership to a ready session or to `OpeningFailure { error, cleanup }`. The caller can preserve the typed opening error and await `OpeningCleanup::wait()` separately. Canceling the completion await leaves the attempt available for explicit cleanup. Before-worker failures return an already-complete cleanup receipt. Initial `Store::open` failure closes its partial connection in the existing helper; the receipt waits for worker completion, not a retained failed connection. The adapter does not recreate that connection. Maintenance failures that actually return a connection or seal retain those resources on their owning thread under the existing lifecycle policy. They are not the same failure path.

The contract requires no second lifecycle thread. Dropping an attempt requests cleanup; it does not certify it. Runtime and owner lifetime must survive until cleanup finishes. The app can retain its location lease while displaying recovery after the failed worker has cleaned up.

For recognized upgrades, choose a unique non-overwriting backup under the host-owned backup directory before mutation. Preserve failed staging evidence. A future fixture upgrade campaign must cap retained backup count and bytes explicitly and refuse an upgrade before mutation when evidence cannot fit. It must not delete evidence to make an attempt fit. Automatic production retention/pruning remains subject to the approved bounded-retention policy and still needs its exact count/size and eligibility decisions. The implemented `SelectedRegistry::begin` adapter is schema-2-only. It acquires ownership, reads the strict selector and validates its named generation before opening. It never initializes storage or searches for a fallback. Both packaged campaign inputs are preseeded schema 2. There is no schema-1 upgrade campaign. Production backup retention and a future upgrade campaign remain separate work.

### Shutdown

Reuse Tauri's continuously driven runtime. Intercept normal application exit before runtime teardown. After ordinary unsaved-writing handling, close application admission, attachments and settings associations; await settings draining, then registry shutdown/opening-attempt cleanup, then release application location ownership and exit. The fixture intercepts exit and awaits draining before calling Tauri exit. The production unsaved-writing flow remains outside this fixture.

The approved cleanup-status threshold is two seconds. The fixture presents a plugin-free Keep waiting status and never automatically force-quits. **A native Force quit action is not implemented.** The full production shutdown UX remains planned. It must include a separate confirmed Force quit action with a real warning: unfinished changes may not be saved, and an operation may already have committed without a delivered response. Waiting cannot forcibly interrupt a blocked callback, SQLite operation or native task. A watchdog kill is failed validation, not successful cleanup.

## Native management boundary

Create the manager from Rust at one fixed application entry. Use a separate frontend build entry with no transitive editor/plugin-host or package imports. The manager may share reviewed application UI utilities, not the existing `+page.svelte` initialization graph. It receives no package-resource associations.

Rust records each live WebView's role, approved entry and fresh random lifetime identifier at native creation. Require the actual invoking WebView from Tauri, the narrow capability route and that active lifetime association at every protected endpoint. Capture and validate the association before asynchronous work and recheck it at operation admission. Frontend role/label fields are never authoritative. Every protected request must also carry the current document-lifetime session marker, obtained from a minimal native session handshake for that actual registered WebView. This marker is required, not optional. A request delayed before native handler entry still carries its old marker and fails after label reuse or document replacement. Bind the marker to the role, entry and native lifetime record; it is never a substitute for actual caller and capability checks. Validate and copy the association before awaiting anything.

On destruction or disallowed navigation, close that lifetime's attachments and invalidate its native authority. Recreating the same label creates a new lifetime. Delayed requests and acknowledgments from the old lifetime cannot target it. Deny navigation outside the fixed shell, popup/new-window creation and editor-driven creation or navigation of the manager. Reload/navigation handling must renew or revoke the lifetime before allowing another document to invoke commands; do not authorize a document merely because it occupies an old label.

Capabilities enumerate application commands by role. No broad core/window/opener permissions are inherited from the normal app. Audit every registered command, Tauri plugin, URI handler and injected link handler. Do not register opener in the fixture. A raw `invoke` from an editor must fail for management routes even with copied identifiers. There are no SQL, filesystem, arbitrary registry-operation, arbitrary window-target or credential-issuance endpoints.

Use separate restrictive CSP/build graphs for manager and workspace entries. Manager scripts and styles are local application assets; deny package/custom-resource script origins, remote scripts, frames, objects, forms and workers unless a reviewed requirement needs one. Allow only the IPC connection sources required by the packaged runtime. Test exact emitted CSP and origins on each platform before claiming enforcement. CSP is defense in depth, not native authorization.

This boundary separates a trusted manager from plugin-hosting WebViews. It does not isolate plugins sharing one workspace or attest that a JavaScript acknowledgment represents honest ledger application. External loading and plugin-native authorization remain outside the fixture.

## Implemented fixture settings command and wire contract

Names below describe internal fixture commands, not plugin SDK exports. Native composition retains `SettingsOperations` only for management and read-only `SettingsAssociation` for workspaces. Every resource write routes through the native coordinator.

| Caller                  | Operations                                                                                         | Restrictions                                                                                                                                           |
| ----------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Known application shell | `session_handshake`, `bootstrap_status`                                                            | Handshake returns version, session, role and next save sequence for the actual registered shell; status exposes no registry path or plugin credentials |
| Manager                 | `settings_read`, `settings_save`, `settings_result`, `settings_application_status`                 | Actual manager lifetime required; save includes full configuration and expected revision                                                               |
| Workspace               | `settings_attach`, `settings_attachment_read`, `settings_ack`, `settings_renew`, `settings_detach` | Own lifetime and attachment only; no setter and no arbitrary target window                                                                             |
| Planned native app menu | Open/focus the manager                                                                             | Not implemented by this fixture; no editor-exposed window creation command                                                                             |

The implemented ordinary command boundary is `{ payload: JSON.stringify(dto) }`. Rust checks the raw string's 4 KiB UTF-8 bound before strict object DTO decoding. `settings_attach` also receives a Tauri channel as `events`. The argument-free `session_handshake` is the only exception; `bootstrap_status` requires the ordinary versioned session payload. Every protected handler checks the actual invoking WebView's fixed entry and its native lifetime record. Role-specific capabilities provide a separate authorization layer. Tauri and WebView internals may allocate incoming data before the application size check.

Use a versioned JSON envelope. A snapshot carries protocol version `1`, a random wire service epoch, a random attachment ID, a canonical decimal delivery sequence, a canonical decimal saved revision and all eight settings using the existing frontend `ReservationLimits` shape. Each request also carries the mandatory document-lifetime session marker. Revisions and sequences use the nonnegative signed-64-bit range; sequences exhaust rather than wrap. Limits remain positive JavaScript-safe integers. Reject unknown fields and invalid shapes. Map the native allocation-based epoch to one wire epoch per settings-service lifetime; never serialize an allocation address. Reattachment creates a fresh attachment, even within the same service.

All attachment IDs bind to the actual WebView lifetime and service. They are routing markers, not bearer authority. An acknowledgment repeats attachment, service epoch, delivery sequence and revision. It releases only that attachment's exact in-progress delivery. Stale or foreign replies never advance application status. Closure is a typed channel message with the association identity and bounded reason, not an apparent default snapshot.

The adapter registers the native subscription before exposing its initial state. Each selected wire delivery retains the exact native subscription snapshot and its native epoch/revision. Only the matching post-application wire acknowledgment calls that subscription's native `acknowledge`. Channel-send success, a save response and an attachment-read response never release delivery capacity or count as application acknowledgment.

Deliver one full snapshot at a time through a Tauri channel; rely on the native subscription's one-latest replacement instead of creating a second history queue. Allocate consecutive delivery sequences only when selecting a snapshot for wire delivery. Coalesced saved revisions can jump without causing a delivery-sequence gap. A repeated delivery retains the same sequence and snapshot. The workspace applies through the existing ledger before acknowledging and remains paused until initial application succeeds. Existing stale/duplicate/inconsistent-message rules still apply. A delivery-sequence gap requires explicit stale state and reattachment, not guessing missing configuration. The confirmed snapshot in a save reply may be older than the current published snapshot; it never directly updates a workspace ledger.

A successful save response carries the confirmed saved snapshot and request ID. A conflict carries the original conflict and its optional later observation. Native uncertainty remains distinct from a transport timeout. On timeout the UI says the save result is unconfirmed; it never reports rollback or automatically submits the write again. A bounded native result record may reconcile that exact request. If it expired or belonged to a destroyed manager lifetime, read authoritative state without claiming that state proves which earlier request committed.

Within a manager lifetime, save request IDs are consecutive canonical decimal sequences, qualified by the required lifetime marker. The session handshake supplies the next sequence. Rust retains a constant-space admitted high-water mark. Reserve a result-record slot and advance that mark together before starting an admitted save. Only the exact next sequence can admit new work. A busy refusal before that reservation does not consume it; there is no capacity-waiting queue. Counter exhaustion requires a new management lifetime, not wraparound.

A retained duplicate with identical expected revision/configuration waits for or returns the same operation. A changed payload is rejected. A sequence at or below the high-water mark with no retained record returns `result-expired`; it is never a new mutation. A gap above the next sequence is rejected. This avoids both write replay and an unbounded set of remembered IDs. Reserve capacity for all pending and completed records. At capacity, evict the oldest completed record if one exists; otherwise reject new admission. Completed records also expire after ten minutes. Expiry or early eviction removes exact-result availability, not the high-water protection.

Native admission owns completion even when the manager closes. Results from a destroyed manager do not grant its replacement authority or revive old attachments. The native coordinator still uses completed async operations; this wire request bookkeeping does not expose a new admitted-write handle in the internal registry API.

`settings_application_status` returns bounded per-workspace saved/applied/pending/stale status. Saved means database commit under the existing policy, not simultaneous window application. Windows can use an older configuration until delivery or detected association failure. A reported acknowledgment is not protection against hostile code in a shared JavaScript environment.

## Liveness, failure and bounded recovery

Channels plus acknowledgments do not alone detect a silent gap in an idle workspace. The approved, implemented periodic health exchange checks the native service/lifetime/attachment latch, not SQLite. It does not introduce repeated settings reads, a database polling loop or automatic service restart.

The initial lease is bounded from the attach challenge's send time on the workspace clock. The attach response must arrive within the attach deadline; initial application and acknowledgment must finish within the delivery deadline. No readiness is exposed with an absent or expired initial lease. After initial application, the trusted workspace adapter issues at most one renewal challenge at a time. A response must match that challenge, service and attachment and report current native validity. Derive the local lease deadline from the challenge's send time on the workspace's monotonic clock, not its receipt time or a cross-process wall clock. Delayed or duplicated replies cannot indefinitely renew an old association. Backend admission rechecks native validity; a response selected before invalidation may still arrive afterward, within the bounded detection window.

Use a single bounded scheduler for active attachments, not a timer/task for every message. On transport failure, malformed messages, lease expiry or a detected gap, mark the client stale and pause new command admission. The ledger's synchronous admission gate must check the monotonic deadline, not depend only on a timer callback. A background/frozen workspace can become stale; after resuming it must reattach before admitting more commands. Existing calls retain their limits and accounting.

The shared internal `SettingsAssociation::closed().await` operation lets transport await settings closure without polling or relying solely on registry validity. Multiple independent waiters may observe the same closure. It does not certify draining. Each admitted attachment owns one bounded delivery/closure task, with cancellation-safe cleanup. Closure can originate from registry invalidation or from the settings service itself. Closing the attachment wakes its task and releases its subscription. Include transport tasks in application draining before settings shutdown. Send native closure promptly when observed. Initial attach, acknowledgment and renewal deadlines bound retained transport state. Timeout never cancels an admitted database write. Reattachment is explicit, including after service replacement; it preserves the existing ledger and counters. A healthy explicit reattach attempt may reread authoritative state, but does not replay a save. There is no automatic retry or restart loop.

### Approved fixture budgets

| Budget                                            | Approved fixture value                                                                                                   |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Workspace attachments                             | 8, at most one active per registered workspace lifetime                                                                  |
| Live manager windows                              | 1                                                                                                                        |
| Admitted settings operations                      | 16 globally; at most one active save per manager lifetime; reject excess immediately                                     |
| Lifecycle / validity readers                      | 8 / 16, separately admitted                                                                                              |
| Native snapshot subscriptions                     | 16; one in-progress and one latest value per subscriber                                                                  |
| Accepted application request or snapshot body     | 4 KiB of UTF-8 JSON; diagnostics capped at 1 KiB; reject oversized/unknown fields                                        |
| Save-result records, pending plus completed       | 32 globally; completed results expire after 10 minutes or oldest-completed capacity eviction; never evict in-flight work |
| Initial attach / delivery acknowledgment deadline | 10 seconds each                                                                                                          |
| Renewal cadence / response deadline / local lease | 10 seconds / 5 seconds / 30 seconds from challenge send time                                                             |
| Cleanup-status display                            | After 2 seconds; no automatic force exit                                                                                 |

Control acknowledgments and renewal have bounded per-attachment admission separate from saves, so a full save budget cannot starve liveness. The request-size limit applies at the application decoding boundary; it is not a claim that Tauri or WebView buffers never allocate a larger incoming message. The raw string check precedes DTO parsing, but not Tauri's allocation of the invoke envelope. The table records approved fixture bounds, not measured capacity, release defaults or a fixed upper limit on the eight resource-setting values themselves. All eight resource-setting defaults and their policies remain approved and unchanged; fixture transport caps are separate.

## Settings UI and command-host adoption

Place Resource limits in the plugin-free manager. Show the eight values, individual reset controls, warnings above defaults and a complete-configuration Save action. Keep drafts on conflict, show the current saved state for review and never silently merge or retry. Show saved versus applied/pending windows independently. Treat request-result uncertainty separately from native transaction uncertainty.

In the fixture, two workspace entries use the opt-in component assembly and its existing settings client. An application-only transport facade supplies the assembly's `resourceSettingsClient` option. Its ledger delegates to the existing client's ledger but first checks the monotonic lease deadline synchronously; on expiry it disconnects the client and rejects admission. It preserves the underlying ledger and counters. The facade owns renewal scheduling and native detachment and disposes them with the assembly. This is a composition wrapper, not a new plugin SDK API or a timer-only change to the existing client.

Native attachment is asynchronous, while the existing service's `subscribe` contract is synchronous. First await the native attach handshake to establish its immutable wire epoch and attachment identity. Buffer at most one early snapshot until that handshake and subscriber registration finish; a terminal closure replaces the buffer rather than queuing behind it. The native unacknowledged delivery prevents an early history from accumulating. A failed/timed-out handshake exposes no service; native attachment deadlines reclaim it. Then attach the client to a service facade with synchronous subscription and an async `read()` backed by `settings_attachment_read`. The local lease and readiness gates apply to both delivery and reads. No automatic reattachment is hidden inside that facade.

Their adapters deliver real native snapshots; they create no second ledger or dispatcher after updates. Include controlled running calls to prove lowered limits and cancellation preserve accounting. Do not modify the default bundled host or Basic Menu as part of transport integration. Production adoption requires a separate explicit component/lifecycle rollout decision.

Planned production recovery UI loads no plugins and keeps existing data intact. The fixture reports pre-window startup failures through bounded native evidence. Once its shell is running, it provides status and controlled shutdown, not functional restore/reset/permission-management actions. Those actions need production request contracts and publication support; do not add disabled-looking controls backed by unsafe shortcuts.

## Packaged fixture and rollout boundary

The implemented prototype at [`prototypes/application-integration/`](../../prototypes/application-integration/README.md) has its own Cargo target, frontend output, identifier, capabilities, build runner and bounded reports. It is opt-in and absent from the normal application build and startup. Reuse shared source modules as the resource prototype does; do not make the application library a public registry SDK or compile globally with `cfg(test)`.

The separate native `seed` executable includes the existing schema initialization and selector codec source through fixture-local module composition. It creates two closed schema-2 inputs and matching selection records in a fresh runner-owned disposable parent. One is the primary registry; the other is a fixed replacement registry at revision `0`. The packaged process then exercises normal selector reading, no-follow layout validation, real owned opening, real settings operations and awaited shutdown. The shared `SelectedRegistry` adapter uses the existing private selector helpers. It is not a production initializer.

The seed is test input prepared before the packaged run. It is not a publication attempt, manufactured publication receipt or durability test. Do not call `publish`, `claim_for_test`, qualification bypasses or candidate publication paths. Preseeding a selector must be reported as preparation, never as proof of successful generation publication. Keep schema definitions and codec bodies shared, not copied into hand-maintained SQL or JavaScript.

Native/runner code selects the disposable parent. The frontend cannot supply paths. Refuse missing fixture configuration; never fall back to real app data. Verify ownership before modifying or cleaning that parent, retain bounded failure evidence outside registry storage, and clean only after all owners/processes finish. A resource cleanup or watchdog failure is a failed run. Successful reporting follows settings, registry and opening-attempt cleanup, not `process::exit` while work remains.

The fixture creates four separate native peers at fixed entries: one plugin-free manager, two workspaces using the real opt-in host and one unauthorized probe. It imports no external plugin package. To test resource authorization rather than just absence of a route, use the existing shared resource helper with one fixed verified inert fixture asset: a workspace read must succeed while a manager/probe read of that same URL is denied by native requester checks. A dedicated denial-test policy may permit the request's connection source while still forbidding package scripts. Report that policy separately from the stricter manager CSP test; neither result substitutes for the other. The asset contains no executable plugin module. Normal app paths, capabilities, CSP and default host remain untouched. A subsequent production rollout must separately resolve publication qualification, actual first launch, recovery actions, retention policy, supported-platform results and command-host adoption. Windows research remains deferred, not waived.

## Implemented campaigns and remaining acceptance

Before calling the fixture complete, require:

- Native tests for owned startup selection, failed-opening cleanup, lock-error classification and retained ownership. Existing empty/malformed roots never become first launch.
- Build/import-graph checks proving management/recovery never imports editor/plugin code. Packaged navigation, popup and resource-request denial tests, not CSP inspection alone.
- Raw-invoke tests denying workspace/probe saves with forged labels, roles, request IDs and copied attachment IDs. Delay old requests before lifetime resolution, then destroy/recreate with the same label; old document markers must fail. Cover document reload/replacement as well as native window destruction.
- Real persistence across clean shutdown/reopen, stale save conflicts, no-ops, abandoned admitted saves, duplicate request IDs, result-capacity saturation/eviction and delayed post-expiry submissions without write replay.
- Initial subscription races, dropped/delayed/duplicate snapshots, acknowledgment backpressure, bounded memory state and blocked workspace behavior.
- Renewal loss, delayed renewal replies, missed timer callbacks and monotonic-deadline admission checks. No new commands after detected stale state; no cancellation or counter reset of admitted calls.
- Native invalidation and explicit reopen with a fresh service epoch, including a lower restored revision from a controlled preseed. No old messages, callbacks or results may retarget.
- Second-process ownership refusal and shutdown draining, including failure/slow-cleanup presentation. A fixture watchdog timeout is never successful cleanup evidence.

The native campaign implements these checks with bounded stage reports. The packaged fresh-service campaign retires old admission, drains old owners, opens the separate fixed revision-`0` input and swaps the stable native router. It destroys and recreates the fixed shells with fresh document lifetimes. Real frontend hosts explicitly attach to the fresh service and report readiness; delayed old-document requests must fail. This does not publish a generation, perform restoration or automatically restart a service. Within a workspace lifetime, explicit transport reattachment retains its existing ledger and counters. Recreated shells start fresh frontend hosts; the campaign does not claim to preserve JavaScript objects across destroyed WebViews.

The runner builds an unsigned debug `.app` and requires both `strict-baseline` and `requester-denial` campaigns. It checks mandatory native stages, source/build attribution, replacement evidence, awaited cleanup and policy-specific resource observations. The strict policy must block resource connectivity. The denial-test policy must observe HTTP 200 for both associated workspaces and 403 for the manager and probe at the same inert asset URL. A partial stage success cannot make an aggregate run pass. See the [changelog](change-log.md#consolidated-application-integration-design) for verified results.

A passing macOS package would not validate Windows, Linux, minimum macOS 13.3, power-loss durability or production publication. Supported-platform qualification remains incomplete. Production storage qualification is blocked, and Windows research remains deferred.
