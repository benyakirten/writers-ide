# Plugin SDK export review

This review records approved exports and proposes the remaining Writer's IDE library exports for external plugin authors. It is based on current package entry points and their application, feature and test consumers. Approval is explicit below; the rest remains proposed. The foundation slice now implements the approved source exports described below. The separate internal Rust parser/static resolver now validates manifest declarations and compatibility. It is not an author SDK export or runtime host service. Production runtime-profile integration remains unimplemented. See the [internal guide](manifest-resolution.md).

The approved direction is an explicit author-facing SDK. Application setup APIs remain separate. Shared Svelte modules and the four foundational ProseMirror packages have their own approved inventory in the [runtime profile proposal](package-api-proposal.md#runtime-profile-inventory).

## How to read this proposal

- **Approved for authors:** selected for the external SDK. Production profile integration and any already-approved validation changes may still be outstanding.
- **Recommend for authors:** useful when implementing an ordinary plugin or provider. These are recommendations, not an approved export list.
- **Application setup:** needed to construct or connect application infrastructure. Preserve access for application code, but do not automatically expose these through the external runtime profile.
- **Needs a decision:** useful functionality whose public boundary or lifetime needs review.

Type exports matter too. A public callback or returned object can expose more operations than the top-level export list suggests. Excluding a TypeScript type does not revoke access to an object already supplied at runtime. This review is a compatibility proposal, not a security boundary.

**Approved first export group:** expose `definePluginApi`, `PluginApi<T>`, `PluginApiIdentity`, `Dispose` and `PluginApiConnection` from `@writers-ide/plugins`. The first three define typed contract identities, not implementations. `Dispose` describes a cleanup function. The host supplies `PluginApiConnection` to a provider factory for a particular consumer connection. Its current contract includes `consumerId`, `signal`, `own`, `reportError` and `guard`. Providers can bind subscriptions and work to that connection without ending unrelated consumers. Early-release cleanup handles are idempotent. The Rust manifest parser enforces the approved API ID byte limit. `definePluginApi` now enforces the same 256 UTF-8 byte ID limit without normalizing valid IDs; the internal alias-based harness checks declarations and runtime access too. The assembled frontend context and application-setup boundary are approved below.

**Approved Svelte UI export group:** expose `defineSveltePresentation`, `SveltePresentation`, `SvelteToolbarContribution` and `SvelteViewContribution` from `@writers-ide/plugins/svelte`. Authors supply ordinary Svelte components and explicit props. The helper type-checks those props and creates a descriptor; it does not mount UI. During activation, authors register descriptors through the host-supplied contribution APIs. The workbench controls placement, rendering and removal. Toolbar orientations can use different components. Registering a view presentation does not open a tab. The Svelte context/entry aliases are approved below. Application registries remain outside the author SDK. It does not add DOM isolation or access to another plugin's UI through the supported contribution API.

The actual `PluginHost` class is in application source, not an export of `@writers-ide/plugins`. Moving it to a new public entry point is not required by this review.

**Representative consumers:** [`plugin-host.ts`](../../src/lib/plugins/plugin-host.ts), [`application-plugin-host.ts`](../../src/lib/plugins/application-plugin-host.ts), [`PluginManager.svelte`](../../src/lib/plugins/PluginManager.svelte), and [`Basic Menu`](../../src/lib/editor/prosemirror/menu/basic/menu.ts).

**Identity types and opt-in no-native assembly implemented:** the external context supplies read-only `identity` with stable canonical `packageId`, stable package-local `componentId`, temporary `activationId` and `projectOpeningId`. Each activation has a fresh activation ID. Project-scoped activations identify their live opening; application-scoped activations use `null` and do not follow selected-project changes. Activation/opening IDs are opaque and must not be used as durable settings keys. This is descriptive metadata, not a native credential or proof of caller authority. See the [context contract](package-api-proposal.md#4-the-activation-context) for the data shape. `ComponentIdentity` and `ActivationIdentity` are approved author-facing data types from `@writers-ide/plugins`. The assembled context is approved below.

**Project-reference type and opt-in in-memory assembly implemented:** export `ProjectReference` from `@writers-ide/plugins`, with read-only string fields `id`, `openingId` and `name`. `context.project` supplies a host-issued reference for a project activation and `null` for an application activation. The local registration ID survives reopening; the opaque opening ID changes, and the name is display text. Project activations remain bound to that opening without following selection. Reference-consuming APIs validate host provenance and live openings; copied fields do not confer access. No filesystem path, manuscript access, native credential or grant is supplied. The application-scoped connection shape is approved below. Project-scoped contexts use `projects: null`, as approved below.

**Project-connection contracts and opt-in in-memory assembly implemented:** expose `ProjectConnections` and `ProjectApiConnection` from `@writers-ide/plugins`, supplying `context.projects` to application-scoped components. The service has `subscribeSelected(listener)` and `connect(project)`. The returned lease has read-only `project`, `signal`, `commands`, and `get`, `subscribe`, `dispose` methods. Exact signatures are in the [context contract](package-api-proposal.md#4-the-activation-context).

Selection subscriptions deliver immediately and on changes, including `null`, and are activation-owned. Connect only valid host-issued live-opening references. Each call creates an independent project-bound lease, not a provider activation. Provider APIs and shared commands use declared project integrations. Missing providers are not enabled; absence alone leaves the lease alive. Idempotent disposal revokes its facades/subscriptions and aborts its signal. Project closure and consumer teardown also end the lease. No native grant or automatic retargeting is implied. Project-scoped contexts receive `projects: null` and use their fixed `project` plus ordinary declared dependencies. Application contexts receive `project: null` and this project-connection service. The draft context type preserves those two combinations. Project-to-other-project connections are future work; an automatic-switching helper remains separately deferred. This is a supported API boundary, not frontend isolation.

**Provider interface and opt-in no-native assembly implemented:** expose `ComponentApis` from `@writers-ide/plugins` as `context.apis`, with `provide(contract, factory)`, `get(alias, contract)` and `subscribe(alias, contract, listener)`. Exact signatures are in the [context contract](package-api-proposal.md#4-the-activation-context). Publish manifest-declared APIs only during synchronous activation. The host supplies `ComponentApiConnection` to factories. Resolve consumer aliases and exact ID/major contracts; declared optional absence yields `null`, while undeclared aliases/contracts and wrong binding routes are author errors. Subscriptions deliver immediately and on availability changes, belong to activation and return idempotent early-release handles. Releasing a subscription does not revoke another use's connection. Required providers resolve before activation; lookups do not enable providers on demand. Selected-project integrations use their explicit lease. No global discovery is added.

**Connection endpoint type and opt-in no-native assembly implemented:** expose `ComponentApiConnection` from `@writers-ide/plugins`. It extends `PluginApiConnection` with read-only `consumer` and `provider` activation identities. External provider factories receive this extended interface while retaining `consumerId`, `signal`, `own`, `guard` and `reportError`. Each identity describes that endpoint's actual activation scope; application endpoints have no project-opening ID even when connected to a project peer. The internal harness requires explicit host identity metadata and adds a fresh activation ID. Its in-memory registry now supplies explicit selection and independent leases, preserving the actual endpoint scopes. It does not implement the application's project UI, filesystem registration or persistence. See the [project guide](project-connections.md). See the [internal connection guide](command-dispatcher.md#alias-based-provider-connections). Use metadata for diagnostics and resource association, not native authority or proof of JavaScript provenance. Providers validate inputs, and native operations remain authorized under the provider's own credential.

**Locale contracts and opt-in application source wiring implemented:** expose `LocaleSnapshot` and `PluginLocale` from `@writers-ide/plugins`, with `context.locale` supplying that service. Snapshots contain read-only `languageTag: string` and `direction: 'ltr' | 'rtl'`. `snapshot()` reads the current UI locale. `subscribe()` delivers immediately and on changes, is activation-owned and returns an idempotent early-release `Dispose`. Listener failures are isolated. This describes the application UI, not manuscript language, and supplies no private translated-message functions. The internal harness requires an explicit host source, freezes delivery snapshots and ties subscriptions to activation rollback/teardown. Nested source changes are serialized. See the [assembly guide](command-dispatcher.md#managed-tasks-and-ui-locale). Plugins own their messages/fallbacks and can use their own libraries or declared translation services.

### Approved SDK assembly

**Implemented source exports and opt-in no-native assembly; external runtime integration pending:** use the root `@writers-ide/plugins` entry point for `FrontendContext`, `FrontendEntry`, `FrontendContributions`, `CommandInvoker`, `PluginCommand`, `CommandRegistration`, `definePluginCommand`, `CommandInvocationErrorCode`, `CommandInvocationError` and `isCommandInvocationError`. Retain the approved provider, identity, project-connection and locale groups above. `ToolbarContribution`, `ViewContribution` and `PluginCapability` are author-facing exports aligned with approved contribution ownership and capability rules.

`FrontendContext<Presentation>` assembles identity, signal, resource ownership, contributions, tasks, provider APIs, commands, locale, native services and scope-specific project access. Project contexts have a fixed `project` and `projects: null`; application contexts have `project: null` and `ProjectConnections`. See the [context contract](package-api-proposal.md#4-the-activation-context). `FrontendEntry<Presentation>` describes the named synchronous activation export, not an in-memory manifest descriptor. Internal `CommandContext<Presentation>` now aliases `FrontendContext<Presentation>`. The harness supplies a frozen complete context with frozen `{ projectFiles: null, externalLinks: null }` native groups and no native authority.

Expose `SvelteFrontendContext = FrontendContext<SveltePresentation>` and `SvelteFrontendEntry = FrontendEntry<SveltePresentation>` from `@writers-ide/plugins/svelte`, alongside its approved presentation and contribution exports. The planned loader will import the verified entry module and call its named `activate` export after checks. It is not implemented. An external Svelte entry module can annotate its parameter as follows:

```ts
import type { SvelteFrontendContext } from '@writers-ide/plugins/svelte';

export function activate(context: SvelteFrontendContext) {
	// Register this component's features through context.
}
```

The types in this example are available workspace exports. The current bundled host does not supply this context. Command types must infer argument-schema input/output and result-schema input/output separately. Caller arguments use argument input, implementation arguments use argument output, implementation returns use result input and caller results use result output. Do not collapse these to a single argument/result pair. `definePluginCommand` now infers all four roles. It validates the contract ID (non-whitespace-only, at most 256 UTF-8 bytes) and positive safe-integer major, then freezes the descriptor. It does not register, execute or validate payloads.

Export `NativeServices` from `@writers-ide/plugins/native` as the context's aggregate of nullable project-file and external-link groups. It describes services; it does not construct them or grant authority.

Keep application registries, management services and bundled descriptors available to application code, outside the external author profile. Do not introduce a public `/host` entry point in this version. The application `PluginHost` stays internal. Official feature plugins use the same author surface as third-party features. This organization is not frontend isolation. Source exports and declarations are implemented. Build/runtime-profile mappings and production integration still need implementation and validation.

The opt-in internal [application assembly](command-dispatcher.md#internal-application-assembly) uses real bar/tab registries, the shared application queue and `createApplicationLocale` over `LocaleManager` (`en`/`fr`, both `ltr`). Stable registry IDs use `component:${placementId}`. It returns `host`, `bars`, `views`, reactive host-only adapter `errors` and `dispose`. It exports no public SDK host constructor and adds no external imports or manifest-to-runtime integration.

The current package root includes both legacy bundled types and the new author contracts. The existing bundled `PluginContext` and host remain unchanged. They do not supply `FrontendContext`, locale/native/project services or typed command invocation. No curated external-profile artifact, loader, native authorizer, database or installer is implemented.

## 3. Managed tasks and workers

Current sources: [`tasks/index.ts`](../../packages-js/tasks/index.ts), [`contracts.ts`](../../packages-js/tasks/src/contracts.ts), [`work-queue.svelte.ts`](../../packages-js/tasks/src/work-queue.svelte.ts), and [`tasks/worker.ts`](../../packages-js/tasks/worker.ts).

### Approved managed-task exports

Expose the following from `@writers-ide/tasks`:

- Task service and handles: `TaskService`, `TaskHandle`, `CooperativeTaskHandle`, `TaskOutcome`.
- Callback inputs and options: `TaskContext`, `TaskOptions`, `CooperativeTaskOptions`, `ForEachTaskOptions`, `AsyncTaskOptions`.
- Progress metadata: `WorkPriority`, `WorkProgress`, `WorkStatus`.

The host supplies an activation-owned task service through the activation context. Authors can run cooperative main-thread work, asynchronous operations and worker work without constructing their own scheduler. Each task returns a handle for results, progress and cancellation. The current `TaskService` also has `dispose()`; it disposes that service's tasks, not the shared queue. Exporting the service contract includes that operation unless a separate reviewed contract changes it.

Cooperative task callbacks must be short. `forEach()` can yield between items, not midway through a callback; `cooperative()` supplies explicit generator yield points. `async()` handles promise-based operations but does not offload CPU work. Authors supply task inputs; these helpers do not read the manuscript. The approval covers this managed-task export group, not scheduler construction or a final external worker-loading signature. Production profile integration remains outstanding.

### Approved worker-side exports

Expose `defineTaskWorker` and `TaskWorkerScope` from `@writers-ide/tasks/worker`. Authors implement one calculation over supplied input; the helper receives one request and sends a result or serialized error. It accepts synchronous or promise-based calculations and an optional result transfer-list callback. `TaskWorkerScope` is the structural message transport contract, useful for actual workers and test transports. Calculations do not receive the editor, DOM or activation context. Use a fresh worker for each invocation; cancellation terminates it.

The worker entry is bundled into each self-contained worker. It is not a window import-map entry and imports no Svelte runtime. Production verified-byte Blob loading still needs integration. The current `WorkerTaskOptions.createWorker` callback describes current library use, not the approved external selection contract below.

### Approved main-thread package-worker selection

**Approved contract; not implemented:** `context.tasks.worker()` selects a packaged worker with a `module` property accepting a `URL` object. Authors construct it relative to their calling frontend module, for example `new URL('./paragraph-lengths.worker.js', import.meta.url)`. Build tooling must preserve or rewrite the reference to the emitted prebuilt worker file.

The host validates that the URL identifies an allowed file in the caller activation's verified package snapshot. Reject foreign-snapshot, arbitrary filesystem and remote URLs; there is no unchecked fallback. Obtain verified bytes, create a fresh Blob worker, send the supplied task input and return the existing task handle. Cleanup terminates the worker and revokes its Blob URL on completion, failure or cancellation, including loading/startup failures.

The external API uses `module: URL`, not a caller-provided `createWorker()` factory. This approval does not remove the current construction callback from standalone library/test use or choose a separate entry-point name. It does not change self-contained worker bundles or add a main-window mapping for worker-side helpers. Remaining option/type integration must preserve approved task ownership, transfer and cancellation policies.

### Approved advanced queue and service exports

Expose `WorkQueue`, `WorkOptions`, `WorkHandle`, `createTaskService`, `TaskServiceOptions` and `TaskFailure` from `@writers-ide/tasks` as advanced author APIs. They remain reusable for independent hosts and tests too. This adds construction tools alongside the managed API; it does not replace or change `context.tasks`.

Use `context.tasks` for ordinary plugin work. Construct an independent queue only when intentionally building a separate scheduling system, such as an embedded tool reused in other applications. A private queue does not participate in the application's shared scheduling budget or automatically inherit activation cleanup. It still runs cooperative callbacks on the main thread and must keep them short.

Authors must supply cancellation, cleanup and error reporting for independently constructed services. Bind a service to the activation signal and own its disposal. Managed services acquire queue scheduling leases automatically. Raw queue users acquire/release their own leases and cancel owned jobs; releasing the last lease only suspends work. See [advanced queue ownership](../../packages-js/tasks/README.md#advanced-use-create-an-independent-queue) for a complete example. Production external-profile integration remains outstanding.

## 4. Optional UI components

Current root exports: [`components/index.ts`](../../packages-js/components/index.ts).

Authors supply labels, icons and action callbacks; these controls contain no formatting rules or native authority.

Support rich tooltip content through Svelte snippets, including author-supplied components. The current general-purpose component wraps trigger content and accepts a named `tooltip` snippet, with explicit target association where needed. `IconButton` includes its tooltip and uses its label when no custom tooltip is supplied. Interactive controls need a separately designed popover/focus contract rather than ordinary tooltip behavior. This export approval does not rename props or introduce a parent-inference API.

**Approved future direction:** expand the optional shared library with selects, comboboxes, virtual lists and other reusable controls. Their APIs, accessibility, focus/keyboard behavior, data contracts and performance need separate review. Do not treat these unimplemented controls as current exports or Part 4 prerequisites. **Approved presentation context; production external integration outstanding:** the host supplies shared tooltip context to registered Svelte toolbar and workspace-view presentations. The host owns the manager, renderer, overlay placement/stacking, docking suppression and their lifetime. Normal plugin controls supply content and labels without creating a manager or mounting an extra renderer. Presentation mounting must preserve this context using the shared components module instance.

Explicitly owned local tooltip scopes are supported through the approved advanced exports below. A separately mounted Svelte root does not inherit host context merely through DOM placement. This approval does not extend that guarantee to arbitrary roots or separately mounted editor node/mark views. Their context integration needs its own review.

**Approved advanced tooltip exports:** expose `TooltipProvider`, `TooltipState`, `Pointer`, `getTooltipManager` and `provideTooltipManager` from `@writers-ide/components`. Document the following advanced-use responsibilities:

- `TooltipState` exposes mutable `open`, `tooltip` and `tooltipEl` state, its `tooltipDebouncer`, timing/positioning fields, and `set()`, `show()`, `dismiss()`, `clear()`, `suppress()`, `attemptCalibration()` and `calibratePosition()`. These reachable operations and fields are included in the advanced author contract.
- Tooltip controls need either an explicit manager or a provider in their Svelte context. The context key comes from a shared module instance. Duplicating the components package can break context lookup.
- The current application provides a manager around the editor and renders one pointer separately. It suppresses that manager during docking. The external presentation context and suppression contract is approved above; production external integration still needs implementation and tests.
- A new Svelte root does not inherit context merely because it is mounted inside the same DOM subtree.
- Providers and controls select their manager during initialization. Changing a manager prop later does not switch their context lifetime.
- A pointer clears its manager when it unmounts. Mounting an extra pointer over a shared manager can interfere with other controls.

Use the host context for normal contributions. For an independent scope, a provider-created manager belongs to that provider; a supplied manager remains caller-owned. Each manager's scope needs exactly one mounted renderer. Do not attach a disposable pointer/provider renderer to the host's shared manager. Context helpers run during Svelte component initialization and do not transfer ownership. Clear local managers and release suppression leases at their appropriate lifetime boundaries; `clear()` does not revoke the manager or release suppression leases. See the [advanced composition guide](../../packages-js/components/README.md#advanced-tooltip-composition).

**Evidence:** [`Tooltip.svelte`](../../packages-js/components/src/Tooltip.svelte), [`TooltipProvider.svelte`](../../packages-js/components/src/TooltipProvider.svelte), [`tooltip-context.ts`](../../packages-js/components/src/tooltip-context.ts), [`tooltip-state.svelte.ts`](../../packages-js/components/src/tooltip-state.svelte.ts), [`+page.svelte`](../../src/routes/+page.svelte), and [`Snippets.svelte`](../../src/lib/editor/prosemirror/menu/basic/Snippets.svelte).

## 5. Layout library

`@writers-ide/layout` is already a reusable library with explicit construction dependencies. That does not make it an API for changing the application's workbench.

Its exports include `createWorkbench`, `BarItemRegistry`, `BarItems`, `HorizontalBarState`, `VerticalBarState`, `FloaterBarState`, `BarTransferHandler`, `LayoutServices`, `DockDraggable`, `DockTarget`, `getDockColor` and their supporting types. Sharing the library does not supply the application's workbench instance. The drag components also depend on `@dnd-kit-svelte/core`, which needs its own runtime/context review.

**Approved advanced library:** include the existing public root exports of `@writers-ide/layout` in the shared author profile, including their supporting types. Preserve its reusable-library role for other hosts too.

This supplies library code, not the application's workbench instance or a supported way to rearrange another feature's UI. Use the contribution APIs to add toolbars to the application. Authors constructing an independent layout own rendering, geometry, drag contexts, focus policy and lifetime cleanup. `createWorkbench()` constructs connected reactive state and transfer machinery; it does not render a full workspace or create central tabs.

**Approved integration policy; not implemented:** expose the public root of `@dnd-kit-svelte/core` as an advanced shared author import, with `0.0.11` as its initial baseline. Plugin-owned drag providers and shared layout components must resolve the same module instance. Other DnD packages/internal paths are not automatically shared imports. Authors retain ownership of independent contexts, without application workbench access or authority over other contributions.

Bundle `@writers-ide/layout/dock-colors.css` as a build-time input into emitted plugin CSS and declare that output through manifest `styles`. ## Shared-command errors

**Implemented error class, guard and invocation normalization in the opt-in assembly:** `CommandInvocationErrorCode`, `CommandInvocationError` and `isCommandInvocationError`. `CommandInvocationError` extends `Error` with required read-only `code` and `diagnosticId` fields. Its constructor takes `(code, message, diagnosticId)`. The helper narrows an `unknown` caught value. Recognition establishes neither origin nor authority.

Normalize command-invocation failures into this contract. Initial codes are `cancelled`, `revoked`, `unavailable`, `invalid-reference`, `contract-mismatch`, `invalid-arguments`, `invalid-result`, `limit-exceeded` and `execution-failed`. See the [code meanings](command-contract.md#invocation-errors). Keep original implementation/validator exceptions available to host diagnostics. These contracts are separate from native-service errors and synchronous editor results. Root command exports are implemented. The guard is a nonthrowing Error-representation and known-code check that supports other JavaScript realms. It does not authenticate origin or grant authority. The approved [safe diagnostics](command-contract.md#safe-diagnostics) add a host-written caller message and diagnostic ID without automatically disclosing payloads or raw exceptions. The exported class implements the required diagnostic-ID field. The guard checks a string diagnostic ID as well as the Error representation and known code; use it across realms or SDK copies where `instanceof` may fail. Construction does not create a host diagnostic record. The [isolated dispatcher](command-dispatcher.md) normalizes failures and delivers safe metadata to host observers. Default bundled-host migration, external integration and diagnostic storage remain outstanding.

## Native service contracts

**Implemented source entry point; services not implemented:** expose native contracts through `@writers-ide/plugins/native`. Export the runtime helper `isNativeServiceError` and types `NativeRequestOptions`, `FileIndexEntry`, `FileIndexStatus`, `FileIndexQueryOptions`, `FileIndexPage`, `ProjectFiles`, `ExternalLinks`, `NativeServices`, `NativeErrorCode` and `NativeServiceError`.

This is a subpath of the plugin package, not a separate package. Importing it grants no permissions. Authorized service instances come from the activation context; Rust checks every protected operation. Export no application service singleton, credentials or raw `invoke` wrapper. No public error constructor is required. Package source exports are implemented; build/runtime-profile mappings and production integration remain outstanding.

The following available imports belong in a plugin module that needs native-service types or error handling. They do not construct services:

```ts
import {
	isNativeServiceError,
	type ProjectFiles,
	type ExternalLinks,
} from '@writers-ide/plugins/native';
```

**Exported native error types and guard; native normalization pending:** `revoked`, `cancelled`, `permission-denied`, `invalid-input`, `unavailable`, `not-found`, `limit-exceeded`, `unsupported-entry` and `io`. Native-service failures reject with structured SDK errors; an identification helper distinguishes them from other caught values. Follow the [code meanings](package-api-proposal.md#native-failures-and-proposed-resource-rules), not message parsing. Additional codes may be added when new distinctions are needed. Unexpected programming exceptions are not automatically native errors or `io`. Approve author exports `NativeErrorCode`, `NativeServiceError` and `isNativeServiceError`. `NativeServiceError` is `Error & { readonly code: NativeErrorCode }`. The helper accepts `unknown` and returns `value is NativeServiceError`. No public error constructor is required initially. Recognition checks the supported representation, not a public class constructor, and establishes neither origin nor authority. The guard is a nonthrowing Error-representation and known-code check that supports other JavaScript realms. Production native normalization and integration remain outstanding. This does not change synchronous editor results or select application-command error codes.

**Approved external-link signature; not implemented:** `ExternalLinks.open(url: string, options?: NativeRequestOptions): Promise<void>`, reached through the nullable `context.native.externalLinks` service. Accept strings only; pass `.href` for JavaScript `URL` objects. Shared options provide cancellation. Resolution means OS acceptance, not page loading; failures reject under the native error contract. Cancellation cannot undo an opened link. Rust enforces permission, HTTP/HTTPS validation and rejection of embedded usernames/passwords. Do not disclose credentials in diagnostics. This service accepts no HTTP method, body or headers and returns no HTTP response. Browser `fetch` remains separate, as does the future native HTTP service. The approved author entry point is `@writers-ide/plugins/native`; build/profile and production integration remain outstanding.

**Approved saved-file read operation; not implemented:** `context.native.projectFiles.read(path, options?)` returns `Promise<Uint8Array>`. The shared author-facing `NativeRequestOptions` data type has optional read-only `signal?: AbortSignal`. Metadata discovery follows the file-index direction below. The metadata contracts below and their `@writers-ide/plugins/native` entry point are approved; build/profile and production integration remain outstanding.

Use paths relative to the activation's registered project. The host supplies credentials and checks the read grant, even when a list-only activation has a non-null file service. These are saved file bytes, not unsaved editor state. Authors decode or parse the result. Cancellation, resource limits and rejecting native errors apply; the signature promises neither writes nor unlimited file sizes. Numerical budgets remain separate decisions.

**Approved file-index direction; not implemented:** metadata discovery will query a project-scoped SQLite index of files and filesystem metadata, not file contents or an authoritative application-document catalog. Finish query statements and transactions before returning pages; retain no filesystem iterator or database statement/transaction between pagination requests. Directory views retain project-relative paths, explicit `'.'` root notation, no-follow unsupported-entry handling and the approved 256-entry response maximum without a caller-selected size.

Native notifications and periodic reconciliation maintain the index. Watcher setup/runtime failure leaves usable records and periodic reconciliation available. Report failure through status/diagnostics, retry setup with increasing delay and reconcile after restoration. Preserve successful initialization history; successful scans must not hide unresolved watcher failure. Closure stops scans, timers and retries. Exact timer/batch/retry defaults remain implementation work. Reconciliation is host-controlled initially. Plugin queries do not request scans. A host-owned user refresh action needs UI/behavior design; plugin scan requests are future work. Change subscriptions use coalesced post-commit invalidation, not raw OS events or per-file batches. They are activation-owned and stop on access revocation/project closure. Queries return available cached/partial metadata with explicit readiness/freshness and the revision used, rather than waiting for initialization/reconciliation to finish. Incomplete empty results do not prove emptiness; failed scans do not prove deletions. Readiness transitions also invalidate subscribers after state becomes query-visible. Ready does not mean instantaneous filesystem consistency, and known-path reads do not depend on readiness. The `FileIndexStatus` data shape is approved: read-only `revision: string`, `initialized`, `reconciling`, `needsReconciliation` booleans, `lastReconciledAt: number | null` and `lastError: string | null`. See its [field meanings](file-index-plan.md#approved-status-shape). This describes background indexing; query failures still reject. Metadata queries, status reads and coalesced subscriptions use `project.files.list`/`project`; saved contents require `project.files.read` separately. A read-only component has no metadata query/status/subscription access. Service-object availability does not grant operations. Raw OS events and manual rescans are not approved. `ProjectFiles.subscribeIndex(listener, options?): Promise<Dispose>` is approved, with initial `FileIndexStatus` delivery before resolution and coalesced subsequent statuses. Reject native setup/authorization failures and handle cancellation during setup without leaks. Preserve activation/access/project cleanup, idempotent early release and isolated listener diagnostics. Native activation gating still applies; await in managed async work or async UI handlers. The `FileIndexEntry` data type is approved with read-only project-relative `path`, file/directory/unsupported `kind`, nullable observed `sizeBytes` and nullable `modifiedAt`. Size is null for directories/unsupported/unavailable values. Modification time is Unix-epoch milliseconds for files/directories or null when unavailable/unsupported. Unknown values are not zero; inspection failures remain visible as uncertainty/error. See the [entry meanings](file-index-plan.md#indexed-entry-metadata). This exposes no contents, link targets, checksums or stable document IDs. Opaque reusable keyset tokens over deterministic non-locale-aware paths are approved. Tokens are scoped to the live opening and directory/query, own no native resources and query current state on reuse. Each page has its own status/revision; deletion of a boundary row does not prevent continuation, while live insertions/renames can require refresh. `ProjectFiles.queryIndex(directory, options?): Promise<FileIndexPage>`, `FileIndexQueryOptions` and `FileIndexPage` are approved. Options add opaque `after?: string` to native cancellation. Pages contain read-only entries, matching status and nullable next token; null means no further indexed rows at query time, not filesystem completeness. Keep each computer's rebuildable index in application-managed local storage outside the project folder. Associate it with the registered project and use a separate database from host settings, installation records and permission grants. Exact local directory and schema are implementation details. Corrupt or incompatible indexes rebuild automatically without user approval. Recovery stops serving unusable cache data, reports status/diagnostics and exposes partial replacement results as uninitialized until initialization succeeds. Preserve project files, grants and host settings; report rebuild failure and bound retries. Build/profile integration, detailed recovery mechanics and timer policy remain open. Saved reads remain filesystem operations with live authorization and containment checks. The index may lag actual files. See the [file-index plan](file-index-plan.md).

## Compiler compatibility

**Approved initial policy; external integration not implemented:** the initial runtime profile does not support Svelte's experimental async compilation mode. Supported builds leave `experimental.async` disabled. Authors can still use ordinary async functions, `{#await}` blocks, managed tasks and workers. This is a supported-build contract, not a guarantee that the host can identify or prevent particular source syntax in arbitrary compiled JavaScript.

Support for non-experimental async compilation is recorded as future work. It needs shared-runtime, pending/error UI, lifecycle, editable-content mounting and pagination tests before profile support is enabled. Enabling the mode affects the shared Svelte runtime; treat it as profile compatibility rather than an isolated plugin preference. The approved initial profile is `writers-ide.frontend/1`, with production browser/client compilation, tracing off and Svelte `5.57.3` as the compiler/runtime baseline. See the [complete dependency baseline](package-api-proposal.md#runtime-profile-inventory). Generate/test the module/export inventory and validate future upgrades against supported plugin output before retaining `/1`; breaking changes require a new profile. Version inspection is not compiled-plugin or packaged-runtime validation. See the [implementation plan](implementation-plan.md#frontend-runtime-compatibility).
