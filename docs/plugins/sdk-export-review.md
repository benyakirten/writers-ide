# Plugin SDK export review

This review records approved exports and proposes the remaining Writer's IDE library exports for external plugin authors. It is based on current package entry points and their application, feature and test consumers. Approval is explicit below; the rest remains proposed. This document does not change runtime exports.

The approved direction is an explicit author-facing SDK. Application setup APIs remain separate. Shared Svelte modules and the four foundational ProseMirror packages have their own approved inventory in the [runtime profile proposal](package-api-proposal.md#candidate-runtime-profile-inventory).

## How to read this proposal

- **Approved for authors:** selected for the external SDK. Production profile integration and any already-approved validation changes may still be outstanding.
- **Recommend for authors:** useful when implementing an ordinary plugin or provider. These are recommendations, not an approved export list.
- **Application setup:** needed to construct or connect application infrastructure. Preserve access for application code, but do not automatically expose these through the external runtime profile.
- **Needs a decision:** useful functionality whose public boundary or lifetime needs review.

Type exports matter too. A public callback or returned object can expose more operations than the top-level export list suggests. Excluding a TypeScript type does not revoke access to an object already supplied at runtime. This review is a compatibility proposal, not a security boundary.

**Approved first export group:** expose `definePluginApi`, `PluginApi<T>`, `PluginApiIdentity`, `Dispose` and `PluginApiConnection` from `@writers-ide/plugins`. The first three define typed contract identities, not implementations. `Dispose` describes a cleanup function. The host supplies `PluginApiConnection` to a provider factory for a particular consumer connection. Its current contract includes `consumerId`, `signal`, `own`, `reportError` and `guard`. Providers can bind subscriptions and work to that connection without ending unrelated consumers. Early-release cleanup handles are idempotent. The approved API ID byte limit still needs implementation. This approval does not finalize the activation context, other export groups or application setup entry points.

**Approved Svelte UI export group:** expose `defineSveltePresentation`, `SveltePresentation`, `SvelteToolbarContribution` and `SvelteViewContribution` from `@writers-ide/plugins/svelte`. Authors supply ordinary Svelte components and explicit props. The helper type-checks those props and creates a descriptor; it does not mount UI. During activation, authors register descriptors through the host-supplied contribution APIs. The workbench controls placement, rendering and removal. Toolbar orientations can use different components. Registering a view presentation does not open a tab. This approval excludes activation-context types and application registries. It does not add DOM isolation or access to another plugin's UI through the supported contribution API.

The actual `PluginHost` class is in application source, not an export of `@writers-ide/plugins`. Moving it to a new public entry point is not required by this review.

**Representative consumers:** [`plugin-host.ts`](../../src/lib/plugins/plugin-host.ts), [`application-plugin-host.ts`](../../src/lib/plugins/application-plugin-host.ts), [`PluginManager.svelte`](../../src/lib/plugins/PluginManager.svelte), and [`Basic Menu`](../../src/lib/editor/prosemirror/menu/basic/menu.ts).

**Approved activation identity metadata; not implemented:** the external context supplies read-only `identity` with stable canonical `packageId`, stable package-local `componentId`, temporary `activationId` and `projectOpeningId`. Each activation has a fresh activation ID. Project-scoped activations identify their live opening; application-scoped activations use `null` and do not follow selected-project changes. Activation/opening IDs are opaque and must not be used as durable settings keys. This is descriptive metadata, not a native credential or proof of caller authority. See the [context contract](package-api-proposal.md#4-the-activation-context) for the data shape. `ComponentIdentity` and `ActivationIdentity` are approved author-facing data types from `@writers-ide/plugins`. Other context fields remain under review.

**Approved project-reference export and context field; not implemented:** export `ProjectReference` from `@writers-ide/plugins`, with read-only string fields `id`, `openingId` and `name`. `context.project` supplies a host-issued reference for a project activation and `null` for an application activation. The local registration ID survives reopening; the opaque opening ID changes, and the name is display text. Project activations remain bound to that opening without following selection. Reference-consuming APIs validate host provenance and live openings; copied fields do not confer access. No filesystem path, manuscript access, native credential or grant is supplied. The application-scoped connection shape is approved below. Project-scoped contexts use `projects: null`, as approved below.

**Approved application project-connection exports; not implemented:** expose `ProjectConnections` and `ProjectApiConnection` from `@writers-ide/plugins`, supplying `context.projects` to application-scoped components. The service has `subscribeSelected(listener)` and `connect(project)`. The returned lease has read-only `project`, `signal`, `commands`, and `get`, `subscribe`, `dispose` methods. Exact signatures are in the [context contract](package-api-proposal.md#4-the-activation-context).

Selection subscriptions deliver immediately and on changes, including `null`, and are activation-owned. Connect only valid host-issued live-opening references. Each call creates an independent project-bound lease, not a provider activation. Provider APIs and shared commands use declared project integrations. Missing providers are not enabled; absence alone leaves the lease alive. Idempotent disposal revokes its facades/subscriptions and aborts its signal. Project closure and consumer teardown also end the lease. No native grant or automatic retargeting is implied. Project-scoped contexts receive `projects: null` and use their fixed `project` plus ordinary declared dependencies. Application contexts receive `project: null` and this project-connection service. The draft context type preserves those two combinations. Project-to-other-project connections are future work; an automatic-switching helper remains separately deferred. This is a supported API boundary, not frontend isolation.

**Approved provider interface export; not implemented:** expose `ComponentApis` from `@writers-ide/plugins` as `context.apis`, with `provide(contract, factory)`, `get(alias, contract)` and `subscribe(alias, contract, listener)`. Exact signatures are in the [context contract](package-api-proposal.md#4-the-activation-context). Publish manifest-declared APIs only during synchronous activation. The host supplies `ComponentApiConnection` to factories. Resolve consumer aliases and exact ID/major contracts; declared optional absence yields `null`, while undeclared aliases/contracts and wrong binding routes are author errors. Subscriptions deliver immediately and on availability changes, belong to activation and return idempotent early-release handles. Releasing a subscription does not revoke another use's connection. Required providers resolve before activation; lookups do not enable providers on demand. Selected-project integrations use their explicit lease. No global discovery is added.

**Approved connection endpoint exports; not implemented:** expose `ComponentApiConnection` from `@writers-ide/plugins`. It extends `PluginApiConnection` with read-only `consumer` and `provider` activation identities. External provider factories receive this extended interface while retaining `consumerId`, `signal`, `own`, `guard` and `reportError`. Each identity describes that endpoint's actual activation scope; application endpoints have no project-opening ID even when connected to a project peer. Use metadata for diagnostics and resource association, not native authority or proof of JavaScript provenance. Providers validate inputs, and native operations remain authorized under the provider's own credential.

**Approved locale exports and context field; not implemented:** expose `LocaleSnapshot` and `PluginLocale` from `@writers-ide/plugins`, with `context.locale` supplying that service. Snapshots contain read-only `languageTag: string` and `direction: 'ltr' | 'rtl'`. `snapshot()` reads the current UI locale. `subscribe()` delivers immediately and on changes, is activation-owned and returns an idempotent early-release `Dispose`. Listener failures are isolated. This describes the application UI, not manuscript language, and supplies no private translated-message functions. Plugins own their messages/fallbacks and can use their own libraries or declared translation services.

The external activation context, shared command helpers, native-service types, locale API and project connections include planned contracts not exported today. Their names and signatures must follow their approved designs and remaining reviews. Do not present them as existing exports merely by adding them to this inventory.

## 2. Word-processing extensions

### Approved consumer group and remaining recommendations

**Approved consumer exports from `@writers-ide/word-processing`:** `wordProcessingApi`, `WordProcessingApi`, `EditorTarget`, `EditorSnapshot`, `WordProcessingSnapshot`, `EditorContext`, `EditorReadOptions`, `EditorEditOptions`, `EditorResult` and `EditorFailureReason`. These are the provider-contract, observation/target and edit/result rows below. The behavior and renderer export groups are also approved below. The editor-command export group is also approved below.

The consumer API supplies observations and synchronous callbacks for inspection and transaction building. Validate targets and revisions before applying edits. Do not retain callback editor objects or unfinished transactions across asynchronous work or cooperative yields. Raw ProseMirror access remains trusted; these checks do not prevent direct operations outside the provider's supported editing path.

This is a ProseMirror-specific provider contract, not a generic plugin-host requirement. Another editing engine may publish its own typed provider API and consumers may request it through declared dependency aliases. This does not automatically replace the existing editor or establish a shared document model between engines; those integrations need separate design. **Approved editor-command exports from `@writers-ide/word-processing`:** `EditorCommandRegistration` and `EditorCommandSnapshot`. Retain the provider's synchronous editor registry alongside `runCommand()`. These support short ProseMirror editing operations, not the typed asynchronous shared application command protocol. Authors need clear guidance on when each applies. The [command selection guide](command-contract.md#choose-an-editor-command-or-an-application-command) explains direct execution, named editor registration, shared feature workflows and composition of the two APIs. This approval does not add upstream `prosemirror-commands` to the shared runtime profile or choose the implementation of project-owned editing commands. Production external-profile integration remains outstanding.

**Approved behavior exports from `@writers-ide/word-processing`:** `EditorBehaviorContext`, `EditorBehaviorRegistration` and `EditorBehaviorSnapshot`. Authors register supported ProseMirror behaviors through `WordProcessingApi.registerBehavior()`, not by directly reconfiguring editor views. The provider creates behavior instances separately for matching views and owns their installation and removal for the consumer connection's lifetime. Authors may supply plugin state, decorations and supported transaction/event hooks. Hooks requiring an immediate result remain synchronous. This behavior-group approval does not approve schema changes; renderer exports have their separate approval below. Large-document work must remain bounded or incremental; a decoration callback that scans the entire manuscript is not a recommended production pattern.

**Approved renderer exports:** expose `EditorRendererContext`, `EditorNodeViewRegistration` and `EditorMarkViewRegistration` from `@writers-ide/word-processing`. Expose `defineSvelteNodeView`, `defineSvelteMarkView`, `SvelteContentDOM`, `SvelteNodeViewProps`, `SvelteMarkViewProps` and `SvelteViewOptions` from `@writers-ide/word-processing/svelte`. Register views for existing schema types through the provider, which owns conflicts, removal and failure handling. Ordinary ProseMirror constructors remain supported; Svelte is optional. For editable Svelte views, keep one stable, unconditional content host empty of Svelte-rendered children and attach it with `use:contentDOM`. ProseMirror owns the editable subtree; Svelte owns the surrounding UI. This approval does not add schema types, redesign pagination or guarantee pagination support for arbitrary custom layouts. Production external-profile integration remains outstanding.

`Dispose` is also re-exported here today. Prefer documenting its canonical import from `@writers-ide/plugins`; retaining this convenience type alias is an export-list detail to review.

- `createWordProcessingService` constructs a provider over supplied editor sources.
- `createWordProcessingConnection` creates a consumer-scoped facade over that service.

`WORD_PROCESSING_PLUGIN_ID` is not part of this approval. It identifies the current bundled provider. External consumers use manifest package/component references and dependency aliases; its inclusion still needs a specific use case.

Authors implement `WordProcessingSources` over views they own, register the service's disposal with activation cleanup, and provide connection-scoped facades through the ordinary provider API. Disposing the service releases its managed resources but does not destroy the underlying views; their owner must arrange view destruction separately. Official feature plugins must not receive private editing shortcuts. Public editing integrations must remain the same for official and third-party features.

## 3. Managed tasks and workers

Current sources: [`tasks/index.ts`](../../packages-js/tasks/index.ts), [`contracts.ts`](../../packages-js/tasks/src/contracts.ts), [`work-queue.svelte.ts`](../../packages-js/tasks/src/work-queue.svelte.ts), and [`tasks/worker.ts`](../../packages-js/tasks/worker.ts).

### Approved managed-task exports

Expose the following from `@writers-ide/tasks`:

- Task service and handles: `TaskService`, `TaskHandle`, `CooperativeTaskHandle`, `TaskOutcome`.
- Callback inputs and options: `TaskContext`, `TaskOptions`, `CooperativeTaskOptions`, `ForEachTaskOptions`, `AsyncTaskOptions`.
- Progress metadata: `WorkPriority`, `WorkProgress`, `WorkStatus`.

The host supplies an activation-owned task service through the activation context. Authors can run cooperative main-thread work, asynchronous operations and worker work without constructing their own scheduler. Each task returns a handle for results, progress and cancellation. The current `TaskService` also has `dispose()`; it disposes that service's tasks, not the shared queue. Exporting the service contract includes that operation unless a separate reviewed contract changes it.

Cooperative task callbacks must be short. `forEach()` can yield between items, not midway through a callback; `cooperative()` supplies explicit generator yield points. `async()` handles promise-based operations but does not offload CPU work. Authors supply task inputs; these helpers do not read the manuscript. The approval covers this managed-task export group, not scheduler construction or a final external worker-loading signature. Production profile integration remains outstanding.

### Approved worker-side exports

Expose `defineTaskWorker` and `TaskWorkerScope` from `@writers-ide/tasks/worker`. Authors implement one calculation over supplied input; the helper receives one request and sends a result or serialized error. It accepts synchronous or promise-based calculations and an optional result transfer-list callback. `TaskWorkerScope` is the structural message transport contract, useful for actual workers and test transports. Calculations do not receive the editor, DOM or activation context. Use a fresh worker for each invocation; cancellation terminates it.

The worker entry is bundled into each self-contained worker. It is not a window import-map entry and imports no Svelte runtime. Production verified-byte Blob loading still needs integration. The current `WorkerTaskOptions.createWorker` callback describes current library use, not the approved external selection contract below.

### Approved main-thread package-worker selection

**Approved contract; not implemented:** `context.tasks.worker()` selects a packaged worker with a `module` property accepting a `URL` object. Authors construct it relative to their calling frontend module, for example `new URL('./paragraph-lengths.worker.js', import.meta.url)`. Build tooling must preserve or rewrite the reference to the emitted prebuilt worker file.

The host validates that the URL identifies an allowed file in the caller activation's verified package snapshot. Reject foreign-snapshot, arbitrary filesystem and remote URLs; there is no unchecked fallback. Obtain verified bytes, create a fresh Blob worker, send the supplied task input and return the existing task handle. Cleanup terminates the worker and revokes its Blob URL on completion, failure or cancellation, including loading/startup failures.

The external API uses `module: URL`, not a caller-provided `createWorker()` factory. This approval does not remove the current construction callback from standalone library/test use or choose a separate entry-point name. It does not change self-contained worker bundles or add a main-window mapping for worker-side helpers. Remaining option/type integration must preserve approved task ownership, transfer and cancellation policies.

### Approved advanced queue and service exports

Expose `WorkQueue`, `WorkOptions`, `WorkHandle`, `createTaskService`, `TaskServiceOptions` and `TaskFailure` from `@writers-ide/tasks` as advanced author APIs. They remain reusable for independent hosts and tests too. This adds construction tools alongside the managed API; it does not replace or change `context.tasks`.

Use `context.tasks` for ordinary plugin work. Construct an independent queue only when intentionally building a separate scheduling system, such as an embedded tool reused in other applications. A private queue does not participate in the application's shared scheduling budget or automatically inherit activation cleanup. It still runs cooperative callbacks on the main thread and must keep them short.

Authors must supply cancellation, cleanup and error reporting for independently constructed services. Bind a service to the activation signal and own its disposal. Managed services acquire queue scheduling leases automatically. Raw queue users acquire/release their own leases and cancel owned jobs; releasing the last lease only suspends work. See [advanced queue ownership](../../packages-js/tasks/README.md#advanced-use-create-an-independent-queue) for a complete example. Production external-profile integration remains outstanding.

Current root exports: [`components/index.ts`](../../packages-js/components/index.ts).

Authors supply labels, icons and action callbacks; these controls contain no formatting rules or native authority.

Support rich tooltip content through Svelte snippets, including author-supplied components. The current general-purpose component wraps trigger content and accepts a named `tooltip` snippet, with explicit target association where needed. `IconButton` includes its tooltip and uses its label when no custom tooltip is supplied. **Approved advanced tooltip exports:** expose `TooltipProvider`, `TooltipState`, `Pointer`, `getTooltipManager` and `provideTooltipManager` from `@writers-ide/components`. - `TooltipState` exposes mutable `open`, `tooltip` and `tooltipEl` state, its `tooltipDebouncer`, timing/positioning fields, and `set()`, `show()`, `dismiss()`, `clear()`, `suppress()`, `attemptCalibration()` and `calibratePosition()`. These reachable operations and fields are included in the advanced author contract.
- Tooltip controls need either an explicit manager or a provider in their Svelte context. The context key comes from a shared module instance. Duplicating the components package can break context lookup.

Use the host context for normal contributions. For an independent scope, a provider-created manager belongs to that provider; a supplied manager remains caller-owned. Each manager's scope needs exactly one mounted renderer. Do not attach a disposable pointer/provider renderer to the host's shared manager. Context helpers run during Svelte component initialization and do not transfer ownership. Clear local managers and release suppression leases at their appropriate lifetime boundaries; `clear()` does not revoke the manager or release suppression leases. See the [advanced composition guide](../../packages-js/components/README.md#advanced-tooltip-composition).

## 5. Layout library

`@writers-ide/layout` is already a reusable library with explicit construction dependencies. That does not make it an API for changing the application's workbench.

Its exports include `createWorkbench`, `BarItemRegistry`, `BarItems`, `HorizontalBarState`, `VerticalBarState`, `FloaterBarState`, `BarTransferHandler`, `LayoutServices`, `DockDraggable`, `DockTarget`, `getDockColor` and their supporting types. It also exposes `@writers-ide/layout/dock-colors.css`.

A plugin could use these to build an independent storyboard or research workspace. That workspace would need its own rendering, drag context, geometry, focus policy and cleanup. Sharing the library does not supply the application's workbench instance. The drag components also depend on `@dnd-kit-svelte/core`, which needs its own runtime/context review.

**Approved advanced library:** include the existing public root exports of `@writers-ide/layout` in the shared author profile, including their supporting types. This covers independent workbench construction, registry/item/bar/floating/transfer classes, configuration and position types, `DockDraggable`, `DockTarget` and docking feedback helpers. Preserve its reusable-library role for other hosts too.

This supplies library code, not the application's workbench instance or a supported way to rearrange another feature's UI. Use the contribution APIs to add toolbars to the application. Authors constructing an independent layout own rendering, geometry, drag contexts, focus policy and lifetime cleanup. `createWorkbench()` constructs connected reactive state and transfer machinery; it does not render a full workspace or create central tabs.

Production profile integration is outstanding. Verify the drag peer's module/context identity and define stylesheet delivery before shipping. The library's existing `dock-colors.css` subpath remains a resource integration requirement, not a promise that CSS is a JavaScript import-map module. This approval does not automatically expose every transitive dependency as a direct author import or grant host singleton access.

## Native service contracts

**Approved initial native error codes; not implemented:** `revoked`, `cancelled`, `permission-denied`, `invalid-input`, `unavailable`, `not-found`, `limit-exceeded`, `unsupported-entry` and `io`. Native-service failures reject with structured SDK errors; an identification helper distinguishes them from other caught values. Follow the [code meanings](package-api-proposal.md#native-failures-and-proposed-resource-rules), not message parsing. Additional codes may be added when new distinctions are needed. Unexpected programming exceptions are not automatically native errors or `io`. Exact type/helper names and final export grouping remain under review. This does not change synchronous editor results or select application-command error codes.

**Approved external-link signature; not implemented:** `ExternalLinks.open(url: string, options?: NativeRequestOptions): Promise<void>`, reached through the nullable `context.native.externalLinks` service. Accept strings only; pass `.href` for JavaScript `URL` objects. Shared options provide cancellation. Resolution means OS acceptance, not page loading; failures reject under the native error contract. Cancellation cannot undo an opened link. Rust enforces permission, HTTP/HTTPS validation and rejection of embedded usernames/passwords. Do not disclose credentials in diagnostics. This service accepts no HTTP method, body or headers and returns no HTTP response. Browser `fetch` remains separate, as does the future native HTTP service. Final native export grouping and production integration remain outstanding.

**Approved saved-file read operation; not implemented:** `context.native.projectFiles.read(path, options?)` returns `Promise<Uint8Array>`. The shared author-facing `NativeRequestOptions` data type has optional read-only `signal?: AbortSignal`. Metadata discovery follows the file-index direction below. Its exact API/types and remaining native export grouping still need review.

Use paths relative to the activation's registered project. The host supplies credentials and checks the read grant, even when a list-only activation has a non-null file service. These are saved file bytes, not unsaved editor state. Authors decode or parse the result. Cancellation, resource limits and rejecting native errors apply; the signature promises neither writes nor unlimited file sizes. Numerical budgets remain separate decisions.

**Approved file-index direction; not implemented:** metadata discovery will query a project-scoped SQLite index of files and filesystem metadata, not file contents or an authoritative application-document catalog. Finish query statements and transactions before returning pages; retain no filesystem iterator or database statement/transaction between pagination requests. Directory views retain project-relative paths, explicit `'.'` root notation, no-follow unsupported-entry handling and the approved 256-entry response maximum without a caller-selected size.

Native notifications and periodic reconciliation maintain the index. Reconciliation is host-controlled initially. Plugin queries do not request scans. A host-owned user refresh action needs UI/behavior design; plugin scan requests are future work. Change subscriptions use coalesced post-commit invalidation, not raw OS events or per-file batches. They are activation-owned and stop on access revocation/project closure. Queries return available cached/partial metadata with explicit readiness/freshness and the revision used, rather than waiting for initialization/reconciliation to finish. Incomplete empty results do not prove emptiness; failed scans do not prove deletions. Readiness transitions also invalidate subscribers after state becomes query-visible. Ready does not mean instantaneous filesystem consistency, and known-path reads do not depend on readiness. The `FileIndexStatus` data shape is approved: read-only `revision: string`, `initialized`, `reconciling`, `needsReconciliation` booleans, `lastReconciledAt: number | null` and `lastError: string | null`. See its [field meanings](file-index-plan.md#approved-status-shape). This describes background indexing; query failures still reject. Metadata queries, status reads and coalesced subscriptions use `project.files.list`/`project`; saved contents require `project.files.read` separately. A read-only component has no metadata query/status/subscription access. Service-object availability does not grant operations. Raw OS events and manual rescans are not approved. `ProjectFiles.subscribeIndex(listener, options?): Promise<Dispose>` is approved, with initial `FileIndexStatus` delivery before resolution and coalesced subsequent statuses. Reject native setup/authorization failures and handle cancellation during setup without leaks. Preserve activation/access/project cleanup, idempotent early release and isolated listener diagnostics. Native activation gating still applies; await in managed async work or async UI handlers. The `FileIndexEntry` data type is approved with read-only project-relative `path`, file/directory/unsupported `kind`, nullable observed `sizeBytes` and nullable `modifiedAt`. Size is null for directories/unsupported/unavailable values. Modification time is Unix-epoch milliseconds for files/directories or null when unavailable/unsupported. Unknown values are not zero; inspection failures remain visible as uncertainty/error. See the [entry meanings](file-index-plan.md#indexed-entry-metadata). This exposes no contents, link targets, checksums or stable document IDs. Opaque reusable keyset tokens over deterministic non-locale-aware paths are approved. Tokens are scoped to the live opening and directory/query, own no native resources and query current state on reuse. Each page has its own status/revision; deletion of a boundary row does not prevent continuation, while live insertions/renames can require refresh. `ProjectFiles.queryIndex(directory, options?): Promise<FileIndexPage>`, `FileIndexQueryOptions` and `FileIndexPage` are approved. Options add opaque `after?: string` to native cancellation. Pages contain read-only entries, matching status and nullable next token; null means no further indexed rows at query time, not filesystem completeness. Keep each computer's rebuildable index in application-managed local storage outside the project folder. Associate it with the registered project and use a separate database from host settings, installation records and permission grants. Exact local directory and schema are implementation details. Corrupt or incompatible indexes rebuild automatically without user approval. Recovery stops serving unusable cache data, reports status/diagnostics and exposes partial replacement results as uninitialized until initialization succeeds. Preserve project files, grants and host settings; report rebuild failure and bound retries. Native export grouping, detailed recovery mechanics and timer policy remain open. Saved reads remain filesystem operations with live authorization and containment checks. The index may lag actual files. See the [file-index plan](file-index-plan.md).

## Compiler compatibility

**Approved initial policy; external integration not implemented:** the initial runtime profile does not support Svelte's experimental async compilation mode. Supported builds leave `experimental.async` disabled. Authors can still use ordinary async functions, `{#await}` blocks, managed tasks and workers. This is a supported-build contract, not a guarantee that the host can identify or prevent particular source syntax in arbitrary compiled JavaScript.

Support for non-experimental async compilation is recorded as future work. It needs shared-runtime, pending/error UI, lifecycle, editable-content mounting and pagination tests before profile support is enabled. Enabling the mode affects the shared Svelte runtime; treat it as profile compatibility rather than an isolated plugin preference. Tracing settings and exact compiler/runtime versions remain separate review items. See the [implementation plan](implementation-plan.md#frontend-runtime-compatibility).
